# ออกแบบระบบอัปเดตเฟิร์มแวร์กล้องจากเว็บ OCR Center

เอกสารออกแบบ ยังไม่ใช่คู่มือใช้งาน — ใช้ตัดสินใจก่อนลงมือเขียนโค้ด

## โจทย์

- กล้อง CM4 ประมาณ 20–30 ตัว user/pass เหมือนกันหมด ต่างกันที่ IP
- ต้องสั่งอัปเดตจากหน้าเว็บ Center ได้ เห็นเวอร์ชันของแต่ละตัว
- **คอนฟิกของแต่ละไซต์ห้ามเปลี่ยน** — ชื่อกล้อง ชื่อที่โชว์บนเว็บ IP ของ PLC ค่าครอป โฟกัส โมเดล URL/Key ของ Center
- ปัญหาที่เจอจริงตอนติดตั้งและต้องแก้ไปพร้อมกัน:
  1. **นาฬิกาเพี้ยน** — CM4 ไม่มีถ่าน RTC ดับไฟแล้วเวลาย้อน ทำให้ TLS ฟ้อง `certificate is not yet valid` และ apt ฟ้อง `no longer signed` → ออกเน็ตไม่ได้เลย
  2. **ต้องผ่าน proxy** — `10.201.0.54` พอร์ตต่างกันตามซับเน็ต (8080 สำหรับ `10.36.181.x`, 3128 สำหรับ `10.41.182.x`)
  3. **พอร์ตที่อนุญาตมีจำกัด** — ต้องรู้ก่อนว่าเส้นทางไหนใช้ได้จริงก่อนจะเริ่มอัป

## สถาปัตยกรรม: กล้องดึงเอง (pull agent)

Center **ไม่** ssh เข้ากล้อง กล้องเป็นฝ่ายถามและลงมือเอง ผ่านช่องทางที่มีอยู่แล้วคือ heartbeat

```
กล้อง                                         Center
  │  POST /api/devices/heartbeat                │
  │  { deviceId, version, commit, updateState,  │
  │    deviceTime, proxy, ports }               │
  ├────────────────────────────────────────────►│
  │                                             │  เทียบเวอร์ชันกับเป้าหมายที่ตั้งไว้
  │  { serverTime, timeDrift,                   │  ดูว่าถึงคิว/ถึงช่วงเวลาที่อนุญาตไหม
  │    update: { version, url, sha256, mode } } │
  │◄────────────────────────────────────────────┤
  │                                             │
  │  1) ตั้งนาฬิกาตาม serverTime (ถ้าเพี้ยน)      │
  │  2) preflight: ดิสก์ / proxy / เส้นทาง        │
  │  3) โหลด bundle จาก Center (พอร์ตเดิม 8090)   │
  │  4) ตรวจ sha256                              │
  │  5) แตกลง releases/<ver> + ลิงก์ shared/      │
  │  6) npm ci เฉพาะเมื่อ lock เปลี่ยน             │
  │  7) สลับ symlink + pm2 reload                │
  │  8) health check 90 วิ ไม่ผ่าน = ย้อนกลับเอง   │
  │                                             │
  │  POST heartbeat (version ใหม่ + ผลการอัป)     │
  ├────────────────────────────────────────────►│  บันทึกประวัติ + แสดงผลบนเว็บ
```

**ทำไมเลือกแบบนี้**

| ข้อจำกัดหน้างาน | วิธีที่แบบ pull แก้ |
|---|---|
| พอร์ตที่อนุญาตมีจำกัด | กล้องต่อออกพอร์ตเดียว: Center:8090 ที่ heartbeat ใช้อยู่แล้ว ไม่ต้องเปิด 22 ขาเข้าเลย |
| user/pass เหมือนกัน 30 ตัว | ไม่ต้องเก็บรหัส ssh ไว้บน Center — ไม่มีรหัสให้หลุด |
| นาฬิกาเพี้ยน | ตั้งเวลาจาก `serverTime` **ทุก heartbeat** ไม่ใช่เฉพาะตอนอัป → apt/git/TLS ใช้ได้ตลอด |
| กล้องออฟไลน์ตอนสั่ง | คำสั่งค้างไว้ที่ Center พอกล้องกลับมาก็อัปเอง ไม่ต้องไล่สั่งซ้ำ |
| 20–30 ตัว | ทยอยเป็นชุด กำหนดช่วงเวลาได้ ไม่กระแทกทั้งไลน์พร้อมกัน |
| proxy คนละพอร์ตตามซับเน็ต | กล้องทดสอบเส้นทางเองแล้วรายงานกลับ Center เห็นทั้ง fleet ว่าตัวไหนเส้นทางไหนใช้ได้ |

## ส่วนที่ 1 — นาฬิกา (แก้ก่อนทุกอย่าง)

นาฬิกาผิด = ออกเน็ตไม่ได้ = อัปไม่ได้ จึงต้องแก้ก่อนขั้นอื่นเสมอ

**ทุก heartbeat** Center ตอบ `serverTime` (ISO + epoch) กลับมา กล้องเทียบกับเวลาตัวเอง:

| ส่วนต่าง | กล้องทำอะไร |
|---|---|
| < 5 วินาที | ไม่ทำอะไร |
| 5 วิ – 2 นาที | ตั้งเวลาใหม่เงียบ ๆ บันทึก log |
| > 2 นาที | ตั้งเวลาใหม่ + แจ้ง Center ว่า `clockFixed` (ขึ้นเตือนบนเว็บว่าเครื่องนี้นาฬิกาไหล น่าจะต้องเปลี่ยนถ่าน RTC หรือไฟดับบ่อย) |

ตั้งเวลาต้องใช้ root จึงใส่สิทธิ์เฉพาะคำสั่งเดียว (ติดตั้งครั้งเดียวโดย `install.sh`):

```
# /etc/sudoers.d/ocr-settime
pi ALL=(root) NOPASSWD: /usr/bin/date -s *, /usr/bin/hwclock -w
```

จำกัดเท่านี้พอ ไม่ให้สิทธิ์อื่น ถ้าเครื่องมี RTC ก็เขียนลง hwclock ด้วยเพื่อให้รอดตอนดับไฟ

**ผลพลอยได้:** apt / git / npm ที่เคยพังเพราะ cert จะหายไปเองทั้ง fleet โดยไม่ต้องไปนั่งสั่ง `sudo date -s` ทีละเครื่องอีก

## ส่วนที่ 2 — ตรวจเส้นทางและพอร์ต (preflight)

กล้องทดสอบเส้นทางเองแล้วรายงานผลมากับ heartbeat Center แสดงเป็นตารางความพร้อมของทั้ง fleet

**สิ่งที่ทดสอบ** (เร็ว ไม่กิน CPU ทำทุก 15 นาที และก่อนอัปทุกครั้ง)

| รายการ | วิธีเช็ค | ใช้ทำอะไร |
|---|---|---|
| Center | `GET {centerUrl}/api/health` | ถ้าไม่ผ่าน = โหลด bundle ไม่ได้ อัปไม่ได้ |
| proxy ที่ใช้อยู่ | `CONNECT github.com:443` ผ่าน proxy ที่ตั้งไว้ timeout 5 วิ | ใช้เป็นทางสำรองและใช้ตอน `npm ci` |
| พอร์ต proxy อื่นในรายการ | ลอง 8080 / 3128 / พอร์ตที่ Center ส่งมาให้ลอง | หาเส้นทางที่ใช้ได้อัตโนมัติเมื่อย้ายซับเน็ต |
| ดิสก์ว่าง | ต้องเหลือ > 1.5 GB | กัน bundle แตกไม่ลง / ดิสก์เต็มกลางคัน |
| RAM ว่าง, โหลด | ประกอบการตัดสินใจ | กันอัปตอนเครื่องกำลังแย่ |
| pm2 + python | process ยังอยู่ไหม | ถ้าตอนนี้ยังพังอยู่ ให้ซ่อมก่อนค่อยอัป |

**รายการ proxy กลาง** ตั้งที่ Center ที่เดียว (`PROXY_CANDIDATES=10.201.0.54:8080,10.201.0.54:3128`) ส่งไปกับ heartbeat กล้องไล่ทดสอบแล้วจำตัวที่ผ่าน — ย้ายกล้องข้ามซับเน็ตแล้วมันหาเส้นทางเองได้ ไม่ต้อง ssh เข้าไปแก้

หน้าเว็บ Center จะมีคอลัมน์ "ความพร้อม": `พร้อม` / `นาฬิกาเพี้ยน` / `ดิสก์ไม่พอ` / `ต่อ proxy ไม่ได้` / `ติดต่อไม่ได้`
ปุ่มสั่งอัปจะกดได้เฉพาะตัวที่พร้อม (สั่งข้ามได้แต่ต้องยืนยัน)

## ส่วนที่ 3 — ตัวไฟล์อัปเดต (bundle)

**Center เป็นคนแจกไฟล์** เพราะ Center มีเน็ตผ่าน proxy อยู่แล้ว และกล้องคุยกับ Center ได้แน่นอน (พอร์ต 8090 ที่ heartbeat ใช้อยู่)

```
Center: [ ดึงจาก GitHub ] หรือ [ อัปโหลด .tar.gz เอง ]
   └─► data/releases/v1.5.0.tar.gz  +  manifest.json  +  sha256
          │
          └─► กล้องโหลดจาก http://center:8090/api/firmware/v1.5.0.tar.gz
```

**manifest.json** ที่มากับทุกรุ่น

```json
{
  "version": "1.5.0",
  "commit": "299b3c4",
  "releasedAt": "2026-09-11T03:00:00Z",
  "sha256": "…",
  "requiresNpm": false,          // true เมื่อ package-lock.json เปลี่ยน
  "requiresPython": false,       // true เมื่อ requirements เปลี่ยน
  "minDiskMb": 1500,
  "notes": "ส่งรูป 1 ใบต่อการอ่าน 1 ครั้ง + รายงานโมเดลและน้ำหนัก"
}
```

`requiresNpm: false` คือกรณีปกติ — อัปแค่ไฟล์โค้ด **ไม่ต้องแตะเน็ตนอกโรงงานเลย** ไม่ต้องพึ่ง proxy ไม่ต้องพึ่ง registry ใช้เวลาไม่กี่วินาที
ถ้ารุ่นไหน dependency เปลี่ยนจริง กล้องถึงจะใช้ proxy เพื่อ `npm ci` และ Center จะเตือนบนหน้าเว็บก่อนสั่งว่า "รุ่นนี้ต้องใช้เน็ต"

**ทางสำรอง**: ถ้าโหลดจาก Center ไม่ได้ (เช่น Center ปิดกลางคัน) กล้อง fallback ไป `git fetch` จาก GitHub ผ่าน proxy ที่ทดสอบไว้แล้ว

## ส่วนที่ 4 — วิธีติดตั้งบนกล้อง (atomic release)

โครงสร้างโฟลเดอร์ใหม่ แยก "ของโปรแกรม" ออกจาก "ของไซต์" เด็ดขาด

```
~/Desktop/OCR-V8.1/
├── shared/                  ← ของไซต์ ไม่มีการอัปเดตไหนแตะ
│   ├── config.json          (ชื่อกล้อง, PLC, ครอป, โฟกัส, โมเดล, Center URL/Key)
│   ├── config/users.json    (บัญชีผู้ใช้เว็บของเครื่องนั้น)
│   ├── .env
│   └── Img/                 (รูปที่เซฟไว้)
├── releases/
│   ├── v1.4.2/              ← เก็บไว้ 2 รุ่นสำหรับย้อนกลับ
│   └── v1.5.0/              ← แตกใหม่ตรงนี้ แล้ว symlink ของใน shared/ เข้ามา
├── current -> releases/v1.5.0
└── update-state.json        ← สถานะการอัป กันไฟดับกลางคัน
```

pm2 ชี้ที่ `current` การอัปคือ **ย้าย symlink** ไม่ใช่เขียนทับไฟล์ ดาวน์ไทม์ประมาณ 2–3 วินาที

**ขั้นตอนบนกล้อง**

| ขั้น | ทำอะไร | ถ้าพัง |
|---|---|---|
| 1 | ตั้งนาฬิกาตาม Center | หยุด แจ้ง `clock-failed` |
| 2 | preflight (ดิสก์/เส้นทาง) | หยุด แจ้งเหตุผล ไม่แตะของเดิม |
| 3 | โหลด bundle → `/tmp` | ลองใหม่ 3 ครั้ง → fallback GitHub → หยุด |
| 4 | ตรวจ sha256 | ทิ้งไฟล์ หยุด แจ้ง `checksum-mismatch` |
| 5 | แตกลง `releases/<ver>` | ลบโฟลเดอร์ที่แตกค้าง หยุด |
| 6 | ลิงก์ `shared/*` เข้าไปในรุ่นใหม่ | หยุด |
| 7 | `npm ci` (เฉพาะ `requiresNpm`) | ลบรุ่นใหม่ทิ้ง หยุด ของเดิมยังทำงานอยู่ |
| 8 | ย้าย symlink + `pm2 reload` | ย้าย symlink กลับทันที |
| 9 | health check 90 วิ: เว็บตอบ + python เริ่มอ่าน | **ย้อนกลับอัตโนมัติ** + แจ้ง `rolled-back` |
| 10 | `pm2 save` + ลบรุ่นเก่าที่เกิน 2 รุ่น | - |

ทุกขั้นเขียนสถานะลง `update-state.json` ก่อนทำ ถ้าไฟดับกลางคัน ตอนบูตมาใหม่ตัวอัปเดตอ่านสถานะแล้วเดินต่อหรือย้อนกลับได้ ไม่ค้างครึ่ง ๆ กลาง ๆ

**ของไซต์ปลอดภัยแค่ไหน:** ตัวอัปเดตเขียนได้เฉพาะใน `releases/` กับ symlink `current` เท่านั้น ไม่มีขั้นตอนไหนเขียนลง `shared/` เลย ต่อให้ bundle เสียหายก็ไม่มีทางลบคอนฟิกของไซต์

## ส่วนที่ 5 — หน้าเว็บ Center

```
┌ Firmware ───────────────────────────────────────────────────────────┐
│ รุ่นล่าสุด: v1.5.0  (299b3c4 · 11 ก.ย. 2026)   [ดึงจาก GitHub] [อัปโหลด] │
│ "ส่งรูป 1 ใบต่อการอ่าน 1 ครั้ง + รายงานโมเดลและน้ำหนัก"                    │
│ รุ่นนี้ไม่ต้องใช้เน็ตบนกล้อง (ไม่มี dependency ใหม่)                        │
├─────────────────────────────────────────────────────────────────────┤
│ ☑ LINE-A-IN   10.1.100.61  v1.4.2  พร้อม           ● ต้องอัป          │
│ ☑ LINE-B-IN   10.1.100.62  v1.5.0  พร้อม           ● ล่าสุดแล้ว       │
│ ☐ LINE-C-OUT  10.1.100.63  v1.4.2  นาฬิกาเพี้ยน 3 ชม ● จะแก้ให้ตอนอัป  │
│ ☐ LINE-D-IN   10.1.100.64  v1.4.0  ดิสก์เหลือ 4%    ● ยังอัปไม่ได้     │
├─────────────────────────────────────────────────────────────────────┤
│ ทยอยครั้งละ [5] ตัว   ช่วงเวลาที่อนุญาต [12:00-13:00] ☑ หยุดถ้าพัง 2 ตัว │
│ [ สั่งอัปเดต ]   [ ย้อนรุ่นก่อนหน้า ]   [ ดูประวัติการอัป ]              │
└─────────────────────────────────────────────────────────────────────┘
```

- **ทยอยเป็นชุด** เพราะ restart = PLC ขาดไป 2–3 วิ ไม่ควรทำทั้งไลน์พร้อมกันระหว่างผลิต
- **ช่วงเวลาที่อนุญาต** กล้องที่ถึงคิวแต่ยังไม่ถึงเวลา จะรอแล้วอัปเองเมื่อถึงช่วงนั้น
- **หยุดถ้าพัง 2 ตัว** กันรุ่นเสียกระจายทั้ง fleet
- **ประวัติ** เก็บทุกครั้ง: จากรุ่นไหนไปรุ่นไหน เวลา ผลลัพธ์ log ท้าย 20 บรรทัด

หน้าเว็บของกล้องเองก็โชว์เวอร์ชันในหน้า System (รุ่น + commit + วันที่ + ปุ่ม "ตรวจหาอัปเดต")

## ส่วนที่ 6 — ความปลอดภัย

Center สั่งกล้องได้ 30 ตัว ถ้าออกแบบพลาด Center ถูกเจาะ = ยึดทั้งโรงงาน จึงจำกัดไว้แต่แรก

| มาตรการ | รายละเอียด |
|---|---|
| Center ส่งได้แค่ "ชื่อรุ่น" | ไม่ใช่คำสั่ง shell กล้องเป็นคนตัดสินใจว่าจะทำอะไรตามขั้นตอนตายตัว — Center ถูกเจาะก็ยิงคำสั่งอะไรก็ได้ลงกล้องไม่ได้ |
| ตรวจชื่อรุ่น | ต้องตรงรูปแบบ `^[A-Za-z0-9._-]{1,40}$` กันพวก `../` หรือคำสั่งแทรก |
| ตรวจ sha256 ก่อนแตะไฟล์ | bundle เพี้ยนหรือถูกแก้ระหว่างทาง = ทิ้ง |
| ลงลายเซ็น HMAC | เซ็น manifest ด้วย API key ที่กล้องกับ Center ใช้ร่วมกันอยู่แล้ว |
| กล้องรับคำสั่งจาก Center ที่ตั้งไว้เท่านั้น | คือ URL ใน config ของตัวเอง ไม่ใช่ใครก็สั่งได้ |
| สิทธิ์ root จำกัด | `/etc/sudoers.d/ocr-settime` ให้เฉพาะ `date -s` กับ `hwclock -w` |
| ไม่มีพอร์ตขาเข้า | กล้องไม่เปิดรับคำสั่งจากใคร เป็นฝ่ายถามอย่างเดียว |

**รายการที่ต้องขอ IT เปิด** (สั้นแค่นี้ ไม่ต้องเปิด 22 ทั้ง fleet)

| จาก | ไป | พอร์ต | ใช้ทำอะไร |
|---|---|---|---|
| กล้องทุกตัว | Center | TCP 8090 | heartbeat + โหลด bundle |
| กล้องทุกตัว | 10.201.0.54 | TCP 8080 / 3128 | proxy (ใช้เฉพาะรุ่นที่มี dependency ใหม่) |
| Center | proxy → GitHub | TCP 8080 / 3128 | ดึงโค้ดมาทำ bundle |

## ส่วนที่ 7 — สิ่งที่ต้องเพิ่มในโค้ด

**ฝั่ง Center**

| ไฟล์ | เพิ่มอะไร |
|---|---|
| `src/db.js` | ตาราง `releases` (version, sha256, manifest, path), `device_updates` (ประวัติ), คอลัมน์ `target_version` ต่ออุปกรณ์/กลุ่ม |

## แผนทำ 3 เฟส

| เฟส | ได้อะไร | ต้องแตะกล้องไหม | เวลา |
|---|---|---|---|
| **1** | นาฬิกาซิงก์จาก Center ทุก heartbeat + preflight + เห็นเวอร์ชันและความพร้อมทุกตัวบนเว็บ | อัปครั้งเดียวด้วย `update-fleet.sh` ที่มีอยู่ | ~1 วัน |
| **2** | Center แจก bundle + โครง atomic release + สั่งอัปทีละตัว/ทั้งกลุ่มจากเว็บ + rollback อัตโนมัติ | ไม่ต้อง (เฟส 1 วางโครงไว้ให้แล้ว) | ~2 วัน |
| **3** | ทยอยเป็นชุด, ช่วงเวลาที่อนุญาต, หยุดเมื่อพัง, ประวัติการอัปย้อนหลัง | ไม่ต้อง | ~1 วัน |

หลังเฟส 2 การอัปครั้งถัดไปทั้ง fleet = กดปุ่มเดียวบนเว็บ ไม่ต้อง ssh ไม่ต้องรู้ IP ไม่ต้องกลัวคอนฟิกหาย

**ทำไมเฟส 1 ต้องมาก่อน:** นาฬิกากับเส้นทางเน็ตคือสาเหตุที่การติดตั้งล้มเหลวเกือบทุกครั้งที่ผ่านมา ถ้ายังไม่แก้สองอย่างนี้ ระบบอัปอัตโนมัติจะพังด้วยเหตุผลเดิม ๆ และเฟส 1 ยังทำให้เห็นภาพรวมทั้ง fleet ว่าเครื่องไหนพร้อม/ไม่พร้อม ก่อนจะให้ระบบลงมือเองจริง

## กรณีพัง — สรุปพฤติกรรม

| เหตุการณ์ | ระบบทำอะไร |
|---|---|
| ไฟดับตอนกำลังแตกไฟล์ | บูตมาอ่าน `update-state.json` ลบรุ่นที่แตกค้าง ใช้ `current` เดิมต่อ |
| ไฟดับตอนสลับ symlink | symlink เป็น atomic operation — ได้ของเก่าหรือของใหม่เท่านั้น ไม่มีสถานะครึ่งทาง |
| รุ่นใหม่ขึ้นไม่ได้ | ไม่มี heartbeat/health ใน 90 วิ → ย้อน symlink กลับเอง แจ้ง Center ว่า `rolled-back` |
| ดิสก์เต็ม | preflight ตัดจบก่อนโหลด ไม่แตะของเดิม |
| นาฬิกาเพี้ยน | ตั้งใหม่จาก Center ก่อนทุกครั้ง |
| proxy ล่ม | รุ่นที่ไม่มี dependency ใหม่ยังอัปได้ปกติ (โหลดจาก Center) รุ่นที่ต้อง `npm ci` จะรอ แจ้ง `needs-network` |
| Center ล่ม | กล้องทำงานต่อตามปกติ (อ่านเลข ส่ง PLC) แค่ไม่มีใครสั่งอัป |
| กล้องออฟไลน์ตอนสั่ง | คำสั่งค้างที่ Center อัปเองเมื่อกลับมาออนไลน์ |
